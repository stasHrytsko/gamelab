# Как собирать прототип игры

Инструкция собрана по трём готовым прототипам: `slide-out`, `build-pack`,
`arrow-flip`. Всё, что у них совпадает, здесь описано как правило. Всё, что
пришлось чинить после показа автору, описано как ловушка. Правила игры берутся
только из спеки (`specs/NN-slug.md`). Этот файл задаёт, **как** игру собрать.
**Что** это за игра, он не решает.

## 0. Когда начинать

- Идея лежит в `ideas/backlog/` с `gate1: approved` в шапке (Gate 1 пройден,
  игра ещё не собрана — в `ideas/approved/` идея переедет последним шагом
  этого же чек-листа, см. ниже и `ideas/gate1.md`).
- Спека `specs/NN-slug.md` закрывает свой Definition of Ready целиком (конец
  файла) и приложен §7.1 (скетч экрана). Если в спеке есть `OPEN`, игру не
  собираем.
- Если есть солвер (`solver: required`), уровни в нём проверены. Уровни
  подбирает солвер, а не человек; где он лежит — смотри у похожей игры
  (`tools/<slug>-solver.mjs` у Arrow Flip, `apps/<slug>/tools/` у Slide Out).

Если чего-то нет, сначала задай вопрос автору. Правило, придуманное по ходу
сборки, — это альтернативная версия игры, а спека такого не допускает.

## 1. Структура — одинаковая у всех

```
apps/<slug>/
  game.json                  карточка на витрине: idea, path, title, genre, pitch (§8)
  index.html                 мета, og, manifest, <div id="app">
  package.json               те же скрипты, меняется только name и порт preview; зависимостей нет
  tsconfig.json vite.config.ts .gitignore     — копия без изменений
  playwright.config.ts       копия, меняется только порт
  public/                    icon-192, icon-512, apple-touch-icon, og.png, manifest.webmanifest
                             (пути в manifest относительные: игра живёт по подпути)
  src/
    main.ts                  hash-роутер: #/  #/levels  #/level/N; VITE_ROUTER=memory для артефакта
    styles.css               @import "@ui/design-tokens.css" + общая оболочка + стили игры
    engine/types.ts          Level, GameState, Status, причины поражения
    engine/<name>Engine.ts   чистые функции правил §4–5, без DOM
    levels/levels.ts         (или levels.json + loader, если уровни генерируются)
    ui/screens.ts            главный + уровни
    ui/game.ts               игровой экран, анимация хода, попапы
    ui/popup.ts feedback.ts storage.ts log.ts icons.ts      — общая оболочка
  tests/engine.test.ts       правила: валидный, невалидный и пограничный исход
  tests/levels.test.ts       решаемость, лимиты, kill-критерий в форме теста
  e2e/play.spec.ts           путь игрока в настоящем браузере
  tools/brand.html make-images.ts build-artifact.ts   (+ генератор/солвер, если есть)
  README.md
```

**Копировать без изменений** (проверено, что у всех трёх игр они совпадают
побайтно): `ui/popup.ts`, `ui/feedback.ts`, `tsconfig.json`,
`vite.config.ts`, `tools/make-images.ts`. Из `main.ts` и `ui/storage.ts`
меняется только ключ `localStorage` (`<slug>:progress:v1`) и импорт уровней.
Проще всего начать с `cp -r` последней игры и удалить из неё механику.

Стек фиксирован: TypeScript strict + Vite, без фреймворка, экран на HTML/CSS,
анимации через Web Animations API и CSS. Тесты — Vitest и Playwright. Новые
зависимости не добавляем. Версии Vite, TypeScript, Vitest и Playwright одни на
весь репо: `devDependencies` корневого `package.json`, игры — npm workspaces.
В `package.json` игры их не дублируем.

## 2. Экраны — одинаковые у всех

1. **Главный.** Арт автора (`UI Design/prototypes/<slug>/assets/`) во весь
   экран, под ним настоящая кнопка «Играть»/«Play»: пилюля 72 px, которая
   дышит, светится и по которой пробегает блик. Кнопку, нарисованную в арте,
   обрезаем. Оригинал кладём в `home-screen.png`, обрезку — в
   `home-art.(webp|png)`. Низ и края арта растворяются в его размытой копии (CSS-маска).
2. **Уровни.** Пять карточек: номер-тайл, «Уровень N», строка с цифрами
   уровня. Состояния: `current` (синяя обводка и ▶), `done` (зелёный тайл и
   ✓), `locked` (замок; при тапе карточка покачивается). Уровень открывается
   победой на предыдущем.
3. **Игровой.** Шапка 44–48 px: слева «к уровням», по центру «Уровень N»,
   справа «?» и «заново». Поле занимает всё оставшееся место. Если игре нужен
   лоток или подсказка, они идут внизу, в зоне большого пальца.
4. **Попапы** (`openPopup`, у всех одинаковые):
   - «Как играть?» — открывается сам при первом входе в уровень 1, дальше по
     «?». Картинка-пример и 4 пронумерованных правила, кнопка «Понятно!»;
   - победа — «Следующий уровень» / «Переиграть» / «К уровням»;
   - финал после уровня 5 — кубок, «Переиграть» / «К уровням»;
   - поражение — красный ✕, заголовок по коду причины, «Переиграть» /
     «К уровням».

Маршруты: `#/`, `#/levels`, `#/level/N`. `?unlock=all` открывает все уровни
для проверки. Прогресс (`passed`, `howToPlaySeen`) хранится в `localStorage`
и дублируется в памяти на случай приватного режима.

## 3. Движок и уровни

- Движок — чистые функции без DOM: `createState(level)` и
  `tap/place/move(state, …) → { state, move } | null`, где `null` означает
  недопустимое действие. Порядок проверок после хода дословно повторяет §5
  спеки.
- Если есть солвер, движок **портирует** его правила без изменений, а тест
  прогоняет решения солвера через движок игры. Правило, записанное дважды,
  разъезжается.
- Солвер, перебор, «жадная стратегия» и подсчёт решений нужны для тестов и
  подбора уровней. **В игре их нет.** Игра не предсказывает проигрыш. Это
  решение автора, повторённое дважды: «хочу сам увидеть, что не могу
  собрать». Поражение наступает только когда ход объективно невозможен или
  исчерпан лимит.
- Никакой случайности, влияющей на исход. Всё зафиксировано в уровне.
- Уровни лежат в `levels.ts` (или генерируются по зерну в `levels.json`). В
  `tests/levels.test.ts` проверяется: каждый уровень решаем, лимит равен
  оптимуму или правилу из спеки, **kill-критерий в форме теста** (жадная
  стратегия или «змейка» не решает уровни с ловушкой), обучающие уровни не
  проигрываются.
- Кривая, которая сработала: 1–2 обучающих уровня без ловушек, 3–5 с ловушкой
  и растущим числом состояний. Пятый уровень проверяет гипотезу напрямую.

## 4. Вид

- Только `UI Design/design-tokens.css` (импорт через алиас `@ui`) и Poppins.
  Новый цвет, радиус или тень — только с одобрения автора, после этого
  обновить токены.
- Игровой объект — тайл кита: градиент от `--c`, тень снизу, блик сверху.
  Цвет задаётся через `--c` на элементе. Если цвет меняется в анимации,
  нужен `@property --c { syntax: '<color>' }` и `transition: --c`.
- У цвета всегда есть второй канал: форма, значок, число. Одним цветом
  информацию не передаём.
- `--ui-danger` оставлен за поражением. «Красный» игровой объект делаем
  через `--ui-coral`.
- Экран помещается без прокрутки от 360×560 до 430×932. Размер клетки
  считается от свободного места (`ResizeObserver` на `.stage`) и ограничен
  min/max из спеки. Первые правки первой игры были именно про раскладку, так
  что поле проверяй на маленьком экране сразу.

## 5. Анимация и отклик

- Числа берутся из спеки: мс на клетку, easing, длительности. Если спека их
  не задаёт, сначала сделай живое демо в `UI Design/prototypes/<slug>/`,
  покажи автору и запиши числа в спеку.
- Анимируются только `transform`, `opacity` и `filter`. Раскладку в анимации
  не трогаем.
- Эффект, привязанный к движению (например, соседа задело), запускается по
  **фактической позиции** объекта на экране (rAF + `getComputedStyle`), а не
  по таймеру. Так синхрон держится при любом easing и на слабом телефоне.
- **Ловушка WAAPI.** `el.animate()` без `fill: 'forwards'` в конце
  откатывает элемент к стилю до анимации. Если между концом анимации и
  `remove()`/`place()` есть хоть одно `await`, на старом месте видна копия
  (баг «призрака» в Arrow Flip). Правило такое:
  - анимация движения всегда идёт с `fill: 'forwards'`;
  - если объект остаётся на поле, после окончания выставь inline-стиль на
    конечное место и вызови `anim.cancel()`;
  - если объект уходит с поля, `cancel()` не вызывай: он держит последний
    кадр до `remove()`.
- Пока идёт анимация хода, ввод заблокирован (`busy`). Попап тоже блокирует
  ввод.
- Недопустимое действие ход не тратит: объект покачивается 160 мс, и есть
  короткая вибрация (`vibrate`).
- Победа: на поле пробегает волна, через 300–700 мс появляется попап.
  Поражение: подсветка, через 900 мс попап.
- `prefers-reduced-motion`: длительности анимаций сводятся к нулю, а
  состояние и отметки остаются.

## 6. Для проверки на игроках (§8 спеки)

- `ui/log.ts` пишет события только на устройство
  (`localStorage['<slug>:log']`, до 1000 штук — все игры на одном домене
  делят ~5 МБ хранилища браузера): `level_start`, событие хода
  со всем, что нужно метрикам §8, `help_open`, `level_win`, `level_fail` с
  кодом причины.
- Коды причин поражения стабильны и совпадают со спекой.
- На каждом интерактивном элементе стоит `data-testid`. На экране игры есть
  `data-status`, `data-busy` и счётчики, по ним e2e ждут окончания хода.

## 7. Проверка перед показом

```sh
npm install          # в корне репо, один раз на все игры
npm run check        # в папке игры: typecheck + vitest + build + playwright
```

e2e обязательно проверяют:
1. путь главный → уровни → уровень 1 («Как играть» открылся сам) → победа →
   уровень 2 открыт;
2. все пять уровней проходятся решением солвера, после пятого показан
   финальный попап;
3. недопустимое действие не тратит ход;
4. проигрыш и «Переиграть» возвращают уровень в начало;
5. на 360×560, 375×560, 390×664 и 430×932 нет прокрутки.

Кроме тестов, **сними скриншоты** всех экранов и середины хода и посмотри на
них глазами. Если анимация сложная, запиши трассу `transform` и `opacity` по
кадрам и проверь, что нет отката и скачка.

## 8. Показ и выкладка

- `npx tsx tools/build-artifact.ts` собирает один HTML (скрипт, стили,
  шрифты и картинки внутри, маршрут в памяти). Его публикуем как артефакт,
  чтобы автор сразу поиграл. При обновлении публикуем в тот же URL.
- В артефакте нет соседних файлов: все картинки встраиваются как `data:`,
  нужны `<meta charset>` и `<title>` (это однажды сломало Slide Out).
- `npx tsx tools/make-images.ts` — иконки и `og.png` из `tools/brand.html`.
  Картинки коммитятся, на Vercel браузера нет. `icon-192.png` — это же и
  иконка карточки на витрине.
- **Витрина.** Все игры живут на одном сайте: `https://<домен>/` — витрина,
  `https://<домен>/<path>/` — игра. Отдельного Vercel-проекта у игры нет.
  Игра попадает на витрину сама, как только в `main` есть её папка с
  `game.json`:

  ```json
  {
    "idea": 24,
    "path": "the-dig",
    "title": "The Dig",
    "genre": "Reveal",
    "pitch": "pitch_en из спеки"
  }
  ```

  `idea` — номер идеи (порядок карточек), `path` — адрес игры (английское
  название, строчными через дефис), `genre` — family из спеки одним словом
  по-английски. Пуш в `main` → Vercel запускает `npm run build` в корне
  (`tools/build-site.mjs`): собирает каждую игру в `dist/<path>/`, витрину — в
  `dist/`. Неизменённые игры берутся из кэша. Игра, которая не собралась,
  пропускается, а сайт выходит с остальными, поэтому **проверь локально**:
  `npm run build && npm run preview` в корне → `http://localhost:4190/`,
  карточка есть, игра открывается по своему `path`.
- README игры повторяет структуру README соседних игр: ссылки, витрина,
  команды, устройство.

## 9. После правок автора

- Каждое решение автора записываем в спеку с датой («решение автора
  YYYY-MM-DD»), затем меняем код. Спека остаётся источником правил.
- Меняется вид — синхронно обновляем `UI Design/prototypes/<slug>/` (скетч
  §7.1, демо, README).
- Перед коммитом снова запускаем `npm run check`.
- Каждый баг, найденный на показе, заносим в приёмку спеки и, если возможно,
  в тест. Если он повторяется между играми, — в этот файл.
